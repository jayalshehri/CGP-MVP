## No QA identifiers

- Controls resolve at execution time by active framework code + control code. A QA
  `control_id` is never read.
- Staging and review UUIDs are derived in a Production namespace (batch
  `uuid5(URL, "cgp-production-portfolio:" + source SHA)`). Project ids come from Production identity.
- The acting user is a Production admin: `--operator-user-id` if given, otherwise the first
  active admin by `user_id`. It is set as the session (`request.jwt.claims`), so
  `created_by`/`archived_by`/review attribution are Production users.

## Policy for the 42 pre-release projects

- All 42 are archived (`archived_at`, `archived_by`, `archive_reason` = the cutover reason).
  Nothing is hard-deleted: `prevent_project_hard_delete` refuses project deletes from 95402 on.
- Status, dates, legacy fields and every relationship stay on them, unchanged:
  58 requirement links, 35 direct control links, 11 gap treatments, 0 linked findings.
  The cutover compares every historical row (and every audit event) before and after.
- No relationship is copied to the new projects. The new projects only get approved
  exact control links from the mapping review (`mapping_review_id`).
- Archived projects stay readable (register scope «المؤرشفة» / «كل المحفظة»).

## Ordering correction

The cutover data cannot run before `20261006102306`:

- `95409` installs `block_portfolio_import_phase1`, which refuses any project whose
  `import_staging_id` is set (verified: "Import activation is disabled in Phase 1").
- `102306` replaces it with `guard_portfolio_activation`. It also adds
  `portfolio_mapping_reviews.source_error`, `cybersecurity_project_controls.mapping_review_id`
  and the unique active-name index. The staging insert, the exact links and the post-check all need these.
- So `102306` moves from step L to before step G. `185235` (hardening) is valid either
  after the data (the QA-proven order) or before it. Both orders were rehearsed locally with
  identical results. It stays after the data, as on QA.
- Steps G–K are one transaction (`PROD_CUTOVER_COMMIT.sql`): a failure anywhere leaves no partial state.

## Backup checklist (A)

1. Supabase dashboard → Database → Backups: confirm PITR is enabled and its window covers
   the change. Without PITR, take an on-demand backup and record its timestamp/id.
2. Run the preflight and store its full output (ledger, counts, GATE, fingerprints).
3. Export to CSV/JSON (outside Git, in `backups/`) and record SHA-256 of each:
   `cybersecurity_projects`, `cybersecurity_project_requirements`,
   `cybersecurity_project_controls`, `cybersecurity_project_gap_treatments`,
   `assessment_findings where project_id is not null`,
   `grc_audit_events where entity_type like 'cybersecurity_project%'`,
   `supabase_migrations.schema_migrations`.
4. Optionally pin the fingerprints into the cutover with `--preimage` (keys `projects`,
   `project_requirements`, `project_controls`) and regenerate. The commit then refuses on any drift.
5. Confirm no credentials, dumps or exports are added to Git.

## Forward recovery

| Failure | Recovery |
|---|---|
| Migration 95402 / 95409 / 102306 / 185235 fails | Each migration is one transaction: nothing is applied. Fix the cause shown by the gate and rerun the same file. Never edit an applied migration. To revert an applied one, write a new migration. For 185235, adapt `qa-portfolio-hardening-forward-recovery.sql` (removes exactly its objects). |
| 102306 index build fails (duplicate names) | Prevented by the preflight gate. Otherwise resolve the duplicate name first (business decision), then rerun. |
| Staging / mapping / archive / import / link error | One transaction: rolls back entirely. Fix and rerun the dry run. The commit is idempotent: a rerun after success writes nothing and re-verifies. |
| Exact code does not resolve in Production | Dry run lists it under `exact_downgraded_to_needs_review`; the commit refuses. Either correct the catalog through its approved process, or (owner-approved) regenerate with `--expected-exact <n>` so the reference stays `needs_review`/pending. Never guess. |
| Data wrong after commit | `PROD_RESTORE_DRILL.sql` (rollback) first, then `PROD_RESTORE_OLD_PORTFOLIO.sql`. The 42 become active again, the imported 43 stay archived with ids, links and audit, and the batch is `cancelled`. Nothing is deleted. |
| App deployment fails | Promote the previous Production deployment (8aa8b93). If the release app cannot be fixed forward quickly, also run `PROD_RESTORE_OLD_PORTFOLIO.sql` so the old app's view is consistent. Schema stays (additive). |
| Last resort | PITR restore to the timestamp recorded at A. This loses all writes after A. |
